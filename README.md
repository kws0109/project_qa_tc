# QATC — 게임 QA 테스트케이스 자동 생성 도구

서브컬쳐 게임(원신, 붕괴:스타레일, 명조, 블루아카이브)을 플레이하면 화면 전이를
자동으로 기록하고, 담당자와 LLM이 함께 검토해 **근거 스크린샷이 붙은 Excel
테스트케이스**를 만듭니다.

```
플레이 녹화  →  화면·전이 분석  →  담당자↔LLM 검토  →  TC 생성  →  xlsx + 다이어그램
```

Windows 전용 · Python 3.11+ · 스탠드얼론 (서버 불필요)

> **작업을 이어받는 경우 [HANDOFF.md](HANDOFF.md) 를 먼저 보세요** — 현재 진행 상황, 실측으로 확인된 사항, 다음에 할 일이 정리되어 있습니다.

---

## 왜 이런 구조인가

**문제**: TC 작성은 전부 수작업입니다. 테스터가 플레이하며 화면을 캡처하고,
"홈 화면 → 캐릭터 버튼 클릭 → 캐릭터 목록 표시"를 엑셀에 손으로 옮겨 적습니다.
플레이 1시간이 TC 작성 3시간을 만듭니다.

**접근**: 플레이를 자동 기록해 **화면 전이 그래프**를 만들고, 그 그래프를 근거로
LLM이 TC 초안을 씁니다. 다만 LLM 혼자서는 "이 화면이 뭐라고 불리는지", "이게 진짜
새 화면인지 애니메이션 중간 프레임인지"를 알 수 없으므로, **담당자와 LLM이 리뷰
화면에서 협업해 흐름을 확정한 뒤** TC를 생성합니다.

### 안전 원칙 — 관찰만 하고 개입하지 않습니다

대상 게임 중 원신/스타레일(`mhyprot2.sys`), 명조(ACE)는 커널 레벨 안티치트가
돕니다. 이 프로그램은 다음을 **절대 하지 않습니다**:

- 입력 주입 (`SendInput`) · 프로세스 메모리 접근 · DLL 인젝션 · DirectX 오버레이 후킹

사용하는 것은 OBS·Discord와 동일한 OS 표준 경로뿐입니다 —
`SetWindowsHookEx` 읽기 전용 저수준 훅 + Windows Graphics Capture.

## 설치

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -e .
pip install -e ".[capture,gui]"     # 캡처 가속 + 리뷰 GUI (권장)
```

Python 3.14까지 검증했습니다. 선택 의존성이 없어도 동작합니다:

| 없으면 | 결과 |
|---|---|
| `windows-capture` / `dxcam` | `mss`로 폴백 (창모드 게임은 정상, 전체화면은 실패할 수 있음) |
| `PySide6` | `qatc review`만 불가, 나머지 전부 동작 |
| API 키 | 화면 이름이 자동 이름으로 남고 TC 생성 불가, 나머지 전부 동작 |

> `paddlepaddle`은 Python 3.14 휠이 없어 **PaddleOCR 대신 RapidOCR**을 씁니다.
> 같은 PP-OCR 모델을 ONNX로 쓰므로 정확도는 같고 용량은 1/3입니다.
> 한국어 모델은 첫 실행 시 자동으로 내려받습니다(약 23MB).

### API 키 등록

```bash
qatc config --set-api-key
```

Windows 자격 증명 관리자에 저장됩니다. 설정 파일에 평문으로 남지 않습니다.
(환경변수 `ANTHROPIC_API_KEY`도 인식합니다.)

코드를 돌리기 전에 **당신의 환경에서 설계 가정이 성립하는지** 확인하세요.

```bash
python scripts/spike.py --profile genshin
```

나머지는 정확도만 낮춥니다.

## 사용법

> ⚠️ **게임이 관리자 권한으로 실행 중이면 녹화도 관리자 권한이어야 합니다.**
> Windows UIPI가 저수준 입력 훅을 차단해 클릭·키 입력이 하나도 기록되지 않습니다
> (화면 캡처는 정상 동작하므로 겉보기엔 녹화가 되는 것처럼 보입니다).
> `qatc record` 가 시작 전에 검사해 차단하고 안내합니다.

```bash
qatc record --profile starrail   # 플레이 녹화 (F9 북마크, F10 일시정지, Ctrl+C 종료)
qatc analyze latest              # 화면 상태와 전이 추출
qatc name    latest              # LLM으로 화면 이름 붙이기
qatc review  latest              # GUI에서 검토·수정          ← 핵심 단계
qatc tc      latest              # 테스트케이스 생성
qatc export  latest              # xlsx + 다이어그램 출력

qatc run --profile starrail      # 위 전부를 한 번에
qatc list                        # 세션 목록
```

세션 인자를 생략하거나 `latest`로 두면 가장 최근 세션을 씁니다.

### 리뷰 워크스페이스

```
┌──────────────┬──────────────────────────┬──────────────┐
│ 스텝 타임라인  │  스크린샷 + 검출 오버레이   │  화면 편집    │
│              │                          │──────────────│
│ 화면 목록     │  ▭요소  ⊕클릭 지점        │  LLM 채팅     │
└──────────────┴──────────────────────────┴──────────────┘
```

- **타임라인**: 플레이 순서대로 스텝을 나열. `⚠` = 검토 필요, `🔒` = 확정됨, `↻` = 자기 전이
- **캔버스**: 검출된 UI 요소 박스와 클릭 지점. 요소를 더블클릭하면 이름을 붙일 수 있음
- **채팅**: "이건 성유물 강화 화면이야", "3번이랑 5번은 같은 화면이야" → LLM이 즉시 반영

**요소에 이름을 붙이는 것이 TC 품질에 가장 크게 기여합니다.**
`화면 (0.42, 0.31) 클릭` 이 `[강화하기] 버튼 클릭` 으로 바뀝니다.

`Ctrl+M` = 선택 화면 병합 · `Ctrl+S` = 저장 (자동 저장하지 않습니다)

## 산출물

### Excel (3시트)

| 시트 | 내용 |
|---|---|
| **테스트케이스** | TC ID / 대·중분류 / 사전조건 / 절차 / 기대결과 / 우선순위 / 유형 / **출처** / 근거 썸네일 |
| **커버리지** | 어떤 TC도 커버하지 않은 전이 목록 — **가장 실무적인 시트** |
| **요약** | 분류·유형·출처별 집계, 세션 메타데이터, 읽는 방법 |

**출처 구분이 핵심입니다:**

| 출처 | 의미 | 색 |
|---|---|---|
| `기록됨` | 실제 플레이에서 관측된 경로. 근거 스크린샷 있음 | 연두 |
| `추론됨` | 화면의 UI 요소에서 LLM이 추론한 **미검증** 케이스 | 주황 |
| `사용자추가` | 리뷰 중 사람이 직접 넣은 것 | 파랑 |

`추론됨`은 실제로 그렇게 동작하는지 검증되지 않았습니다. 이 구분이 없으면
LLM 환각이 정식 TC로 둔갑하고 리뷰어는 구분할 방법이 없습니다.

### 플로우 다이어그램

Mermaid `stateDiagram-v2`. GitHub·Notion에 붙여넣으면 바로 렌더링됩니다.
**빨간 점선 = 테스트되지 않은 경로.**

## 아이콘 사전

**텍스트 없는 아이콘이 이 파이프라인의 가장 큰 구멍입니다.** OCR과 LLM은 글자가 있는
UI만 알아봅니다. 아이콘만 있는 버튼(기원, 가방, 우편…)은 무엇인지도, 누르면 무슨 일이
나는지도 모르므로 TC 절차가 `화면 (0.42, 0.31) 위치 클릭`으로 남습니다.

담당자가 **한 번** 지정하면 게임 단위로 영구 저장되고, 이후 모든 세션에 자동 적용됩니다.

### 등록

리뷰 GUI에서 두 가지 경로가 있습니다.

| 경로 | 언제 |
|---|---|
| 캔버스에서 요소 **더블클릭** | OpenCV가 잡은 아이콘 (주황 점선으로 표시됨) |
| **아이콘 영역 지정** 켜고 드래그 | 검출되지 않은 아이콘 (ESC로 해제) |

### 자동 제안 — 이름만 채우면 됩니다

플로우 그래프가 이미 "이 클릭 → 캐릭터 화면 이동"을 알고 있으므로 초안이 채워진 채로
열립니다:

```
이름:      [           ]  ← 이 칸만 입력
동작유형:  이동            (자동)
대상화면:  캐릭터 목록      (자동)
기대결과:  캐릭터 목록 화면이 표시된다   (자동)
```

이름을 자동으로 채우지 않는 이유: 화면 전이만으로는 그 그림이 "기원"인지 "워프"인지
알 수 없습니다. 틀린 이름을 미리 넣으면 무심코 승인해 사전이 오염됩니다.

### 구조화된 동작이 TC에 직접 꽂힙니다

| 필드 | TC에서 쓰이는 곳 |
|---|---|
| `기대 결과` | **기대 결과 칸에 그대로** |
| `소모 재화` | **'재화 부족' 경계값 TC 자동 제안** |
| `되돌리기 불가` | **우선순위 High 자동 판정** |
| `동작 유형` | 유형별 검증 포인트를 LLM에 전달 |

### 데이터가 쌓일수록 정교해집니다

매칭은 이미지 기반 2단계입니다.

```
1단계  dHash 정확 매칭     게임 아이콘은 같은 에셋이라 픽셀 단위로 일치
2단계  디스크립터 kNN      색 히스토그램 + 엣지 방향 + 셀 평균 → 코사인 kNN
3단계  위치·화면 tie-break  동점일 때만
```

2단계가 학습 부분입니다. 확정할 때마다 샘플이 늘고 kNN이라 재학습 없이 즉시 반영됩니다.
오분류를 "이건 A가 아니라 B야"로 고치면 샘플이 옮겨져 결정 경계가 조정됩니다.

> **오매칭이 미매칭보다 나쁩니다.** 못 알아보면 좌표로 남을 뿐이지만, 잘못 알아보면
> "[구매] 클릭 → 재화가 차감된다"처럼 사실과 다른 TC가 나옵니다. 그래서 자동 라벨링은
> 신뢰도 0.90 이상만 적용하고, **한 아이콘이 한 화면에서 하나만** 차지하도록
> 상호 최선 매칭을 강제합니다.

### 조회

```bash
qatc icons                    # 게임별 사전 목록과 통계
qatc icons starrail           # 등록된 아이콘 상세
qatc icons starrail --export 백업폴더
```

저장 위치는 `%APPDATA%/qatc/icons/<게임>/` 입니다 — **세션 폴더가 아닙니다.**
세션을 지워도 사전은 남아야 "쌓인다"가 성립합니다.

## 동작 원리

### 1. 녹화 — 이벤트 트리거 다단 캡처

60fps를 전부 저장하면 1시간에 20만 프레임입니다. 실제로 필요한 건 "입력 직전"과
"전이 완료 후"뿐입니다.

- 상시 **2fps 메모리 링버퍼** (디스크에 안 씀)
- 입력 발생 시: `T-100ms`(링버퍼에서 회수) + `T+250/700/1500ms`
- 입력 없이 화면이 크게 바뀌면 자동 스냅샷 (컷씬·로딩·자동진행)

서브컬쳐 게임은 화면 전환 페이드가 0.5~1초입니다. 클릭 직후 한 장만 찍으면
반투명 중간 프레임이 잡혀 상태 식별이 통째로 무너집니다.

### 2. 분석 — 변동성 학습

**이 프로젝트에서 가장 중요한 기법입니다.** 캐릭터 대기 모션과 파티클 때문에
원본을 그대로 해시하면 같은 홈 화면이 매 프레임 다른 화면으로 잡힙니다.

화면을 격자(32×18=576셀)로 나눠 셀마다 "얼마나 자주 변하는가"를 학습하고,
**안정적인 셀만** 비교합니다. 변동 셀 = 캐릭터·이펙트, 안정 셀 = 패널·버튼·탭
= 화면의 정체성입니다.

세 신호를 결합해 판단합니다:

| 신호 | 강점 | 약점 |
|---|---|---|
| 셀 시그니처 | 빠르고 정확, 항상 유효 | 테마가 바뀌면 흔들림 |
| 구조 시그니처 | 색·글자가 달라도 배치로 판단 | 요소 검출이 불안정할 때 잡음 |
| 텍스트 시그니처 | 탭 이름이 같으면 강력 | 텍스트 없는 화면에선 무력 |

애매한 쌍(회색 구간)만 LLM에 물어보고, 판정은 클러스터링의 하드 제약이 됩니다.
연결 방식은 **complete linkage** — 과병합을 막는 가장 보수적인 선택입니다.

### 3. 검토 — 3층 데이터 모델

```
auto : 프레임에서 재계산 가능 (해시, 검출 박스, OCR)
llm  : API 재호출로 재생성 가능 (이름, 역할, 분류)
user : 사람이 확정한 것 — 절대 자동으로 덮어쓰지 않음
```

분석 파라미터를 바꿔 재분석하거나 프롬프트를 고쳐 재생성해도 `user` 층은
살아남습니다. 리뷰 30분이 재실행 한 번에 날아가지 않게 하는 유일한 장치입니다.

## 비용

세션 하나(화면 40개 · TC 생성 포함) 기준 **약 $2~3**입니다.

| 단계 | 모델 | 비중 |
|---|---|---|
| 경계·예외 TC | Opus 5 (고해상도 이미지) | **~76%** |
| 정상 경로 TC | Opus 5 | ~16% |
| 화면 명명 | Sonnet 5 | ~3% |
| 동일성 판별 | Sonnet 5 | ~2% |

비용의 대부분이 경계·예외 TC입니다 — 유일하게 고해상도 스크린샷을 보내는
단계이기 때문입니다. 통제 수단:

```bash
qatc config --set-budget 3.0     # 세션 예산 (초과 시 호출 차단)
qatc tc latest --happy-only      # 추론 TC 생략
```

`llm.max_derived_screens`(기본 24) 설정이 이 비용을 직접 결정합니다.
`qatc tc`는 실행 전 예상 비용을 보여주고 확인을 받습니다.

## 게임 프로파일

`profiles/*.yaml`에 게임별 창 탐색 규칙, 캡처 영역, 무시 영역, LLM 배경 지식을
둡니다. 제공되는 프로파일: `genshin`, `starrail`, `wuwa`, `bluearchive`.

```yaml
name: 원신
window:
  title_regex: "^(原神|Genshin Impact|원신)$"
  process: GenshinImpact.exe
capture_roi: full            # 에뮬레이터는 [0.0,0.045,0.955,0.955] 처럼 툴바 제외
ui_language: ko
static_ignore:
  - {x: 0.86, y: 0.0, w: 0.14, h: 0.055, why: "우측 상단 시계"}
llm_context: |
  호요버스의 오픈월드 액션 RPG. 주요 화면 계층은 ...
```

> **블루아카이브는 에뮬레이터**로 구동하므로 `capture_roi`로 BlueStacks 툴바를
> 잘라내야 합니다. 첫 실행 시 캡처 영역이 게임 화면과 맞는지 확인하세요.

## 구조

```
qatc/
├─ models.py       데이터 모델 (3층 분리)
├─ storage.py      SQLite + 프레임 파일
├─ config.py       설정 · API 키(keyring)
├─ profiles.py     게임 프로파일
├─ capture/        WGC / DXGI / GDI 3중 폴백 + 창 추적
├─ record/         입력 훅 · 링버퍼 · 다단 캡처
├─ analyze/        변동성 · 해시 · UI검출 · OCR · 클러스터링 · 플로우
├─ icons/          아이콘 사전 · 디스크립터 · 매칭 · 자동 제안
├─ llm/            클라이언트 · 명명 · 판별 · TC생성 · 채팅 · 비용
├─ review/         PySide6 리뷰 워크스페이스
├─ export/         Excel · Mermaid
└─ cli.py
```

의존 방향은 `analyze → llm`이 **없습니다**. LLM 없이도 파이프라인이 돌아간다는
성질을 구조로 보장합니다.

## 개발

```bash
pytest                                    # 129개 테스트
python scripts/make_fixture.py            # 합성 게임 세션 생성 (게임 없이 파이프라인 검증)
qatc analyze fixture_synthetic --no-llm
```

`scripts/make_fixture.py`는 서브컬쳐 게임의 까다로운 특성(캐릭터 애니메이션,
파티클, 전환 페이드, 변하는 재화 수량, 한글 UI)을 의도적으로 재현합니다.
정답은 **화면 4개 · 전이 6개**이며, 파이프라인이 정확히 그 값을 내야 합니다.

## 알려진 제약

- **Windows 전용** — 캡처와 입력 훅이 Win32 API에 의존합니다.
- **자동 실행(리플레이) 없음** — 설계상 제외했습니다. 입력 주입은 안티치트가
  매크로로 오인할 수 있고, 게임 자동화는 타이밍·해상도 문제로 매우 불안정합니다.
- **OCR 정확도 약 80%** — 게임 폰트(외곽선·그림자) 특성상 한계가 있습니다.
  그래서 OCR을 보조 신호로만 쓰고 주 신호는 셀 시그니처입니다.
- **전투 화면은 상태 식별이 어렵습니다** — 화면 전체가 이펙트로 덮여 안정 셀이
  거의 없습니다. 메뉴·UI 중심 플로우에 적합합니다.
