## 1. 배경과 목적

QATC의 원래 방향은 **게임 플레이를 녹화해 화면 전이를 추출하고 거기서 TC를 뽑는 것**이었다.
붕괴:스타레일 실측까지 마쳤으나, 이 경로에는 구조적 한계가 있었다.

- 버튼의 기능은 **실제로 눌러본 것**에서만 알 수 있다. 2026-08-13 세션 실측 결과
  검출 요소 1,358개(노이즈 포함) 중 기능이 밝혀진 것은 8개(0.6%)였다.
- 모든 버튼을 눌러 보는 것은 애초에 피하려던 수작업 그 자체다.

방향을 바꾼다. **사용자가 컨텐츠와 그 기능을 설명하면, 도구가 대화로 정보를 끌어내
게임 구성 요소와 시나리오를 파악하고 그에 맞춰 TC를 작성한다.**

핵심 통찰은 **시작 시점의 정보량이 결과를 좌우한다**는 것이다. 컨텐츠가 무엇인지
모른 채 "이 화면에 버튼이 뭐가 있나요"를 묻는 것과, 개괄을 먼저 듣고 "층 이동은
어떻게 하나요"를 묻는 것은 전혀 다른 인터뷰다. 그래서 인터뷰 1단계를 컨텐츠 개괄로
고정한다.

### 결정된 요구사항

| 항목 | 결정 |
|---|---|
| 입력 방식 | 대화형 인터뷰 — 도구가 질문하고 사용자가 답한다 |
| 인터뷰 단위 | 기능/모듈 단위 (화면 단위·목표 단위 아님) |
| 1단계 | 컨텐츠 개괄 — 항상 여기서 시작 |
| 추론 범위 | 기본 동작 + **설명에 직접 근거가 있는 예외**. 근거 없는 범용 QA 패턴은 만들지 않는다 |
| 인터뷰어 | **Claude Code 세션** (Anthropic API 직접 호출 아님) |
| 사용 범위 | 1인 사용. 팀 배포 계획 없음 |

### 왜 Claude Code 세션인가

당초 설계는 `qatc interview` 가 Anthropic API를 직접 호출해 인터뷰 루프를 도는
것이었다. Claude Code 세션을 인터뷰어로 쓰는 쪽으로 바꾼 근거는 셋이다.

**비용.** API 직접 호출 시 컨텐츠 1개당 약 $0.46이 든다 (인터뷰 15턴 $0.08 +
TC 생성 9계열 $0.38, 프롬프트 캐시 반영). 스타레일 규모면 컨텐츠가 20~30개이고
슬롯을 보강해 재생성하는 것이 정상 워크플로라 실제로는 $30~70이 된다. 절대액보다
성격이 문제다 — **재생성마다 과금되면 재생성을 안 하게 되고, 이 도구의 핵심 루프가
죽는다.** 구독 정액이면 이 문제가 사라진다.

**구현량.** 대화 루프, 프롬프트 조립, 컨텍스트 압축, 재개, LLM 재시도, 예산 추적이
전부 harness의 몫이 된다. 직접 만들면 설정값 튜닝과 재개 버그를 떠안는 부분이다.

**유실 내성.** 사용자 답변이 Claude Code 트랜스크립트와 `knowledge` DB 양쪽에
남는다. `qatc slot set` 이 실패해도 답변 자체는 트랜스크립트에 있어 다시 묻지 않아도
된다. 원래 설계에서 최우선 원칙으로 잡았던 "사용자 답변을 먼저 커밋한다"가 공짜로
이중화된다.

**잃는 것과 그 대가.** 시스템 프롬프트를 완전히 통제하지 못하므로 인터뷰 규칙의
강제력이 약해지고, 인터뷰 루프 자체를 테스트할 수 없게 된다. 전자는 매 질문 전
`qatc slot status` 호출을 스킬에 못박아 완화하고, 후자는 **핵심 불변식을 CLI 경계로
옮겨** 해결한다 (§6 참조). 팀 배포 시에는 팀원마다 구독이 필요하지만 배포 계획이
없으므로 무관하다.

### 역할 분담

```
Claude Code 세션 ──▶ 대화, 컨텍스트 관리, 재개, 자연어 판단
qatc CLI        ──▶ 저장, 커버리지 계산, 불변식 강제
```

**harness는 대화를, 코드는 규칙을 맡는다.** 이 도구의 실패 모드는 "질문을 못 해서"가
아니라 **"빠뜨린 걸 모른 채 TC를 뽑아서"**다. 누락된 TC는 테스트되지 않은 기능이
된다. 그래서 커버리지 추적과 계열 게이트는 프롬프트가 아니라 코드가 지킨다.

## 2. 범위

### 포함

- `knowledge/` 저장소 — 게임별 컨텐츠 지식 슬롯
- `qatc slot` / `qatc knowledge` / `qatc tc` CLI 하위명령
- 인터뷰를 진행하는 Claude Code 스킬
- TC 계열 게이트 (`tc plan` / `tc add`)
- 미충족 슬롯 리포트
- xlsx 출력 (기존 `export/excel.py` 재사용, 제어문자 sanitize 버그 수정 포함)

### 제외

- 화면 캡처·입력 훅·화면 클러스터링·OCR·아이콘 사전 (`capture/` `record/` `analyze/`
  `icons/` `review/`, 약 8,000줄)
- **Anthropic API 직접 호출 경로** (`llm/` 전체). 인터뷰와 TC 작성은 Claude Code
  세션이 수행하므로 `LlmClient`·`CostTracker`·`naming`·`tcgen`·`disambiguate`가
  이 방향에서는 쓰이지 않는다
- 스크린샷을 인터뷰 보조 입력으로 쓰는 기능 (향후 확장 여지로만 남긴다)

기존 미사용 코드는 **삭제하지 않는다.** 녹화 파이프라인이 나중에 "이 화면 보면서
설명할게요" 형태로 되살아날 여지가 크다. 다만 `qatc` CLI에서 해당 명령을 숨겨
사용자가 혼동하지 않게 한다 — `--legacy` 플래그를 붙였을 때만 노출한다.

### 이 방향에서 다루지 않는 기존 버그

2026-08-13 세션 분석에서 발견했으나 녹화 파이프라인에 속해 이번 범위 밖인 것들.
기록만 남긴다.

1. `list_sessions()`가 폴더 이름 역순 정렬이라 `latest`가 `fixture_synthetic`을 고름
   (`storage.py:437`). 정렬 키를 `session.started_at`으로 바꿔야 한다.
2. `_maybe_idle_snapshot()`에 입력 직후 억제 구간이 없어 전이 애니메이션을 "자동 진행"
   으로 오인. 실측 세션 전이 32건 중 11건(34%)이 이 유령 전이였다. 더불어 쿨다운 중
   `_last_idle_ref`를 갱신하지 않아 두 번째 오발이 사실상 보장된다 (`recorder.py:237`).
3. `is_ignored_key()`가 완전일치라 `ctrl_l`이 `ignore_keys: [ctrl]`을 통과
   (`profiles.py:62`). 같은 파일의 `canonical_modifier()`를 쓰면 된다.
4. `click_coords_reliable()`이 수식키 상태만 봐서 메뉴 클릭까지 전부 "좌표 불확실"로
   표시. 실측 11건 중 실제 포인터 잠금은 1건뿐이었다 (`profiles.py:71`).
5. 녹화 종료용 `Ctrl+C`가 게임 입력으로 기록되고, 게임이 `C`를 받아 캐릭터 화면을
   열어 가짜 상태·전이가 생성됨.

**단, 아래 항목은 이번 범위에 포함된다** — `export/excel.py`에 openpyxl 셀 값
sanitize가 없어 제어문자가 들어오면 `IllegalCharacterError`로 export 전체가 실패한다.
새 도구도 같은 익스포트를 쓰므로 반드시 고친다.

## 3. 전체 구조

```
Claude Code 세션 (인터뷰어)
   ↕ Bash
qatc CLI (저장소 + 커버리지 + 계열 게이트)
   ↕
knowledge/<game>.db
```

### 명령 표면

Claude Code가 호출하는 것 (인터뷰 중 · TC 작성 시):

```bash
qatc slot status <컨텐츠> --game <G> [--json]   # 슬롯 상태 (질문 전 매번)
qatc slot init   <컨텐츠> --game <G> --types 편성,성장
qatc slot set    <컨텐츠> <키> --status filled|unknown|na --value "..."
qatc slot add    <컨텐츠> <키> --hint "..." --family "..."
qatc tc plan     <컨텐츠>                       # 만들 계열 목록 (게이트)
qatc tc add      <컨텐츠> --family <계열> --origin interview|inferred --json -
```

사용자가 직접 쓰는 것:

```bash
qatc knowledge --game <G>       # 컨텐츠별 커버리지 한눈에
qatc tc plan   <컨텐츠>          # 무엇이 빠졌는지 확인
qatc tc list   <컨텐츠>          # TC + 미충족 슬롯 리포트
qatc export    <컨텐츠>          # xlsx
```

`tc plan` 은 양쪽에 걸친다 — Claude Code에게는 작성 대상 목록이고, 사용자에게는
"무엇이 아직 안 만들어졌고 왜인지"를 보는 창이다.

**기존 명령과의 충돌 처리.** `qatc tc` 와 `qatc export` 는 이미 존재하며 지금은
**세션**(녹화 결과)을 인자로 받는다 (`cli.py:588`, `cli.py:599`). 두 명령을
**컨텐츠 기반으로 재정의한다** — 인자는 세션 ID가 아니라 컨텐츠 이름으로 해석하고
`knowledge/<game>.db` 에서 찾는다. 세션 기반 경로는 `record` · `analyze` · `name` ·
`review` · `run` · `list` · `icons` 와 함께 `--legacy` 뒤로 숨긴다.

### 권한 설정 — 전제 조건

Claude Code가 매 슬롯 기록마다 권한 승인 창을 띄우면 인터뷰가 성립하지 않는다.
`.claude/settings.json` 에 접두 와일드카드 allowlist를 둔다. (이미 작성됨)

```json
{
  "permissions": {
    "allow": [
      "Bash(.venv/Scripts/qatc.exe slot *)",
      "Bash(.venv/Scripts/qatc.exe knowledge *)",
      "Bash(.venv/Scripts/qatc.exe tc *)",
      "Bash(.venv/Scripts/qatc.exe list *)",
      "Bash(.venv/Scripts/qatc.exe export *)",
      "Bash(.venv/Scripts/python.exe -m pytest *)"
    ]
  }
}
```

규칙은 **명령 문자열의 접두사**로 매칭된다. 따라서 인터뷰 스킬은 이 형태를 그대로,
앞에 `cd` 등을 붙이지 않고 호출해야 한다. `record` · `config` 는 일부러 제외했다 —
캡처 시작과 대화형 키 등록은 매번 승인을 받는 것이 옳다.

### 저장 단위 — 게임 하나당 DB 하나

```
knowledge/starrail.db
  contents    컨텐츠(기능) 레코드 — 파티편성, 유물장착, 워프…
  slots       컨텐츠별 지식 슬롯
  testcases   생성된 TC (+ generated_hash, slot_keys)
```

게임 단위로 묶는 이유는 **누적**이다. 유물 장착을 인터뷰할 때 이미 아는 파티 편성
지식을 컨텍스트로 주면 "파티에 든 캐릭터의 유물을 바꾸면 파티 화면에 반영되나요?"
같은 교차 질문이 가능해진다. 같은 것을 두 번 설명하지 않아도 된다.

`turns` 테이블은 두지 않는다 — 대화 로그는 Claude Code 트랜스크립트가 보관한다.

### 인터뷰 흐름

```
1단계 · 개괄
   스킬이 고정 문구로 시작
   사용자 자유 서술 → Claude Code가 유형 판정 → qatc slot init --types ...

2단계 · 인터뷰 루프
   ┌─ qatc slot status <컨텐츠> --json      ← 매 질문 전 필수
   │  비어 있는 슬롯 중 하나를 골라 자연스럽게 질문
   │  사용자 답변 → qatc slot set ... (한 답변에서 여러 슬롯 가능)
   └─ 커버리지를 사용자에게 표시

3단계 · 종료
   슬롯이 다 차면 TC 생성을 제안한다. 강제 종료는 하지 않는다.
   미충족 슬롯은 지우지 않고 '미확인'으로 남긴다.

4단계 · TC 생성
   qatc tc plan <컨텐츠>   → 만들 계열 목록
   Claude Code가 그 계열만 작성 → qatc tc add (계열 검증)
```

### 핵심 설계 판단

**슬롯 세트를 개괄 단계에서 동적으로 확정한다.** 고정 스키마면 가챠 컨텐츠에 "층 이동"
을 묻는 헛질문이 나온다. 개괄로 유형을 판정한 뒤 슬롯을 조립하면 이 문제가 사라진다.

**미충족 슬롯은 지우지 않고 남긴다.** TC 생성 시 그대로 경고가 된다 — "실패 조건
미확인이라 실패 경로 TC를 만들지 않았음". 누락이 조용히 사라지지 않게 하는 장치다.

**질문 전에 항상 `slot status` 를 읽는다.** 프롬프트 기억보다 결정론적 출력이 믿을 수
있고, 컨텍스트 압축 직후 이미 물어본 것을 다시 묻는 문제도 같이 막힌다.

### 모듈 배치

새로 만드는 것:

| 모듈 | 역할 |

| `qatc/knowledge/store.py` | 게임별 DB 읽기/쓰기 |
| `qatc/knowledge/slots.py` | 기본 슬롯 + 유형별 슬롯 조립 규칙 |
| `qatc/knowledge/gate.py` | `tc plan` 계열 계산, `tc add` 검증 |
| `qatc/cli.py` (확장) | `slot` · `knowledge` · `tc` 하위명령 |
| `.claude/skills/interview/SKILL.md` | 인터뷰 진행 규칙 |

그대로 재사용하는 것:

| 모듈 | 쓰는 것 |
|---|---|
| `qatc/models.py` | `TestCase` · `Priority` · `TCKind` · `TCOrigin` |
| `qatc/export/excel.py` | xlsx 출력 (sanitize 수정 후) |
| `qatc/config.py` | 경로 설정 |

`qatc/llm/` 은 이 방향에서 호출되지 않는다. 삭제하지 않고 남긴다.

## 4. 지식 모델

### 기본 슬롯 — 모든 컨텐츠 공통

각 슬롯이 **어떤 TC 계열을 만드는지**를 함께 못박는다. 이것이 "설명에 근거가 있는
예외만 만든다"를 코드로 강제하는 방법이다. 슬롯이 비어 있으면 그 계열 TC는 아예
생성 대상에서 빠진다.

| 슬롯 키 | 묻는 것 | 만드는 TC 계열 |
|---|---|---|
| `overview` | 이 컨텐츠가 무엇이고 왜 쓰는가 | (TC 없음 — 문맥) |
| `unlock` | 언제부터 쓸 수 있는가 | 미해금 상태 접근 |
| `entry` | 어디서 어떻게 들어가는가 | 진입 경로 |
| `screen` | 무엇이 보이고 무엇을 누를 수 있는가 | 요소 표시 확인 |
| `core_action` | 이 컨텐츠의 주 동작 | **정상 경로** |
| `constraints` | 정원·상한·중복 제한 등 | 경계값 (0 / 최대 / 초과) |
| `cost` | 무엇을 소모하는가 | 재화 부족 |
| `failure` | 안 되는 경우와 그때 피드백 | 실패 경로 |
| `result` | 성공하면 무엇이 어디에 반영되는가 | 결과 검증 |
| `exit` | 저장 시점 · 취소 가능 여부 | 미저장 이탈 / 취소 |

`overview`와 `core_action` 둘만 채워도 정상 경로 TC는 나온다. 나머지는 채울수록
예외 TC가 붙는다.

### TC 계열 → `TCKind` 대응

`TCKind`는 기존 열거형을 그대로 쓴다. 계열이 어느 값으로 떨어지는지 고정한다.

| TC 계열 | `TCKind` | 기본 `Priority` |
|---|---|---|
| 정상 경로 | `HAPPY_PATH` | High |
| 진입 경로 | `HAPPY_PATH` | High |
| 결과 검증 | `HAPPY_PATH` | High |
| 경계값 | `BOUNDARY` | Medium |
| 재화 부족 | `EXCEPTION` | Medium |
| 실패 경로 | `EXCEPTION` | Medium |
| 미해금 상태 접근 | `EXCEPTION` | Low |
| 미저장 이탈 / 취소 | `REVERSE` | Medium |
| 요소 표시 확인 | `UIUX` | Low |

`INTERRUPT`는 이 설계의 어느 계열도 만들지 않는다. 진술에서 중단 상황(통신 끊김,
앱 강제 종료)이 도출되는 경우가 없기 때문이다. `slot add`로 사용자가 그런 항목을
추가하면 그때 쓴다.

`Priority`는 위 값을 기본으로 두되 TC를 쓰는 Claude Code가 진술 내용에 따라 조정할
수 있다 — 재화를 소모하는 동작은 되돌릴 수 없으므로 한 단계 올리는 식이다.

### 유형별 추가 슬롯

개괄을 듣고 Claude Code가 유형을 판정해 `slot init --types` 로 넘긴다.
**복수 적용 가능** — 워프(가챠)는 가챠형이면서 상점형이다.

| 유형 | 추가 슬롯 |
|---|---|
| 가챠/뽑기 | 확률 공개 위치, 천장, 픽업 규칙, 연차 할인 |
| 편성/조합 | 정원, 중복 제한, 프리셋 수, 저장 시점 |
| 강화/성장 | 재료, 성공률, 실패 시 손실, 최대치 |
| 전투/던전 | 층·웨이브, 실패 페널티, 재도전 조건, 제한시간 |
| 상점/구매 | 재고, 갱신 주기, 구매 한도, 환불 |
| 임무/퀘스트 | 수락 조건, 진행 판정, 보상 수령, 만료 |

**슬롯 키 중복 병합 규칙.** 복수 유형이 적용되면 같은 키가 겹칠 수 있다 (예: 가챠형과
상점형 모두 재화 관련 슬롯을 요구). 이때는 **먼저 조립된 것을 남기고 뒤엣것을 버린다.**
조립 순서는 `기본 슬롯 → --types 인자 순서`이므로, 기본 슬롯이 항상 우선하고 유형
간에는 앞에 적힌 쪽이 이긴다. `prompt_hint`와 `tc_family`도 이긴 쪽 값을 쓴다.

### 슬롯 상태 — 4단계

```python
class SlotStatus(str, Enum):
    EMPTY   = "empty"     # 아직 안 물어봄
    FILLED  = "filled"    # 사용자가 답함
    UNKNOWN = "unknown"   # 사용자가 "모른다"고 답함
    NA      = "na"        # 이 컨텐츠엔 해당 없음
```

`NA`가 없으면 사용자가 "이건 재화 안 써요"라고 답해도 도구가 계속 재화를 묻는다.
`UNKNOWN`과 `NA`를 나누는 이유는 TC 생성 시 취급이 다르기 때문이다 — `NA`는 조용히
넘어가고, `UNKNOWN`은 **"확인 필요"로 리포트에 남긴다.**

### 슬롯 값은 자유 텍스트

```python
@dataclass
class Slot:
    key: str
    prompt_hint: str                       # 이 슬롯이 뭘 묻는지 (질문 생성용 힌트)
    tc_family: str                          # 이 슬롯이 만드는 TC 계열
    status: SlotStatus = SlotStatus.EMPTY
    value: str = ""                        # 사용자 답변 (자연어 그대로)
```

값을 구조화하지 않는다. "파티는 최대 4명"에서 경계값 0/4/5를 뽑는 것은 TC를 쓰는
Claude Code가 하면 된다. 중간에 숫자 파싱 계층을 두면 "4명 (단, 서포트 포함 5명)"
같은 실제 답변에서 바로 깨진다. **커버리지는 `status`가, 의미는 텍스트가 담당한다.**

## 5. 인터뷰 스킬

`.claude/skills/interview/SKILL.md` 에 인터뷰 진행 규칙을 둔다. 프로젝트 스킬이므로
이 저장소에서 작업할 때만 로드된다.

### 1턴은 고정 문구

개괄 질문은 항상 같으므로 스킬에 그대로 적어 둔다. 도입부가 흔들리지 않는다.

```
[파티편성] 인터뷰를 시작합니다. 붕괴 스타레일 · 새 컨텐츠

먼저 이 컨텐츠가 어떤 것인지 설명해주세요.
플레이어가 무엇을 하는 곳이고, 왜 쓰는지 편하게 적으시면 됩니다.
```

답변을 받으면 유형을 판정하고 슬롯 세트를 만든다:

```bash
qatc slot init 파티편성 --game starrail --types 편성
qatc slot set  파티편성 overview --status filled --value "..."
```

### 질문 규칙

스킬에 명시할 것:

- **질문 전에 반드시 `qatc slot status <컨텐츠> --json` 을 호출한다.** 프롬프트 기억에
  의존하지 않는다
- 한 번에 **1~2개만** 묻는다. 5개를 나열하면 인터뷰가 아니라 설문지가 된다
- `filled` / `na` 인 슬롯은 절대 다시 묻지 않는다
- 사용자가 "모른다" / "해당 없음"이라고 하면 캐묻지 말고 `unknown` / `na` 로 닫는다
- 답변이 모호하면 다음 슬롯으로 넘어가지 말고 그 자리에서 되묻는다
- 한 답변에 여러 슬롯의 정보가 있으면 `slot set` 을 **여러 번** 호출한다

마지막 항목이 중요하다. 개괄 답변 하나가 진입 경로·정원·재화를 동시에 담고 있으면
그 자리에서 슬롯 4개가 차고, 도구는 그것들을 다시 묻지 않는다. **컨텍스트 우선으로
시작하는 이득이 여기서 나온다.**

### 진행 표시

```
당신: 파티는 최대 4명이고, 같은 캐릭터를 두 번 넣을 수는 없습니다.

  ✓ constraints 기록됨
  [7/12 채움 · 남은 것: 재화, 실패 조건, 저장 시점, 해금 조건, 결과 반영]

도구: 파티를 적용하는 순간이 언제인가요? [파티 적용] 버튼을 눌러야 저장되는지,
      아니면 슬롯을 바꾸는 즉시 반영되는지 궁금합니다.
```

슬롯이 채워질 때마다 즉시 표시한다. 사용자가 "지금 뭐가 기록됐는지"를 그 자리에서
확인할 수 있어야 잘못 기록된 것을 바로 고친다. 인터뷰가 끝난 뒤 전체를 검토하게 하면
아무도 안 본다.

### 재개

Claude Code 세션이 끊기거나 컨텍스트가 압축돼도 `qatc slot status` 한 번이면 복구된다.
슬롯이 곧 대화의 요약이므로 별도 재개 로직이 필요 없다. 새 세션에서 같은 컨텐츠를
인터뷰하면 채워진 슬롯을 건너뛰고 빈 슬롯부터 이어간다.

## 6. TC 생성 — 게이트가 불변식을 지킨다

### `tc plan` — 코드가 계열을 결정한다

```bash
$ qatc tc plan 파티편성
정상 경로       core_action    filled
진입 경로       entry          filled
경계값          constraints    filled
결과 검증       result         filled
미저장 이탈     exit           filled
요소 표시 확인  screen         filled

제외됨:
  재화 부족     cost           empty     ← 슬롯 비어 있음
  실패 경로     failure        unknown   ← 사용자가 모른다고 답함
  미해금 접근   unlock         na        ← 해당 없음
```

Claude Code는 **출력된 계열만** 작성한다.

### `tc add` — 계열을 검증한다

```bash
$ qatc tc add 파티편성 --family 재화부족 --json -
오류: '재화부족'은 이 컨텐츠의 생성 대상이 아닙니다 (cost 슬롯이 비어 있음).
      qatc tc plan 파티편성 으로 대상 계열을 확인하세요.
```

**이것이 설계 전체의 안전장치다.** 인터뷰어가 Claude Code로 바뀌면서 "빈 슬롯 계열은
만들지 않는다"를 프롬프트로만 부탁하게 될 뻔했는데, `tc add` 가 거부함으로써 코드
강제가 유지된다. 프롬프트가 규칙을 어겨도 결과물은 오염되지 않는다.

### 출처 등급 추가

```python
class TCOrigin(str, Enum):
    RECORDED  = "기록됨"     # 기존. 이 방향에서는 미사용
    INTERVIEW = "인터뷰"     # 신규. 사용자가 진술한 내용에 직접 근거
    INFERRED  = "추론됨"     # 진술에서 도출
    USER      = "사용자추가"
```

"파티 적용을 누르면 파티가 바뀐다"는 사용자가 **말한 것**이고, "5명을 넣으면 거부되어야
한다"는 "최대 4명"에서 **도출한 것**이다. 전자가 틀리면 사람 기억이 틀린 것이고
후자가 틀리면 도구가 헛짚은 것이라, 테스터가 의심할 지점이 다르다.
`export/excel.py`가 이미 `origin`별로 셀 색을 칠하므로 그대로 붙는다.

`tc add` 는 `--origin` 을 필수로 받는다.

### rationale에 출처 슬롯을 남긴다

```python
TestCase(
    category_major = "파티 편성",
    category_minor = "경계값",
    title          = "정원을 초과해 5번째 캐릭터를 넣으면 거부된다",
    precondition   = "파티 편성 화면, 슬롯 4개가 모두 채워진 상태",
    steps          = ["빈 슬롯이 없는 상태에서 캐릭터 목록의 5번째 캐릭터를 선택한다"],
    expected       = ["추가되지 않는다", "정원 초과 안내가 표시된다"],
    kind           = TCKind.BOUNDARY,
    origin         = TCOrigin.INFERRED,
    rationale      = "constraints 슬롯: '파티는 최대 4명, 같은 캐릭터 중복 불가'에서 도출",
)
```

`rationale`에 **어느 슬롯의 어떤 문장에서 나왔는지**를 적는다. TC를 의심할 때 근거를
되짚을 수 있어야 하고, 사용자 진술이 나중에 바뀌면 어떤 TC를 다시 만들어야 하는지도
이것으로 찾는다.

녹화 전용 필드(`evidence_frames` · `state_path` · `edge_ids`)는 빈 값으로 둔다.

### 미충족 슬롯은 리포트로 드러낸다

```
$ qatc tc list 파티편성
TC 23건 (정상 6 · 경계값 5 · 예외 4 · 역방향 3 · UI/UX 5)

⚠ 다음 항목이 미확인이라 해당 TC가 없습니다
   cost      (무엇을 소모하는가)      → 재화 부족 TC 없음      [비어있음]
   failure   (안 되는 경우와 피드백)   → 실패 경로 TC 없음      [사용자가 모름]

   이어서 채우려면 Claude Code에서 파티편성 인터뷰를 재개하세요.
```

누락을 조용히 넘기지 않는 것이 이 도구의 핵심 안전장치다. 화면에 안 뜨는 누락은
테스트되지 않은 기능이 된다.

### 재생성은 병합

슬롯을 더 채우고 TC를 다시 만들면 **기존 TC를 지우지 않는다.**

- 계열별로 비교해 새로 채워진 슬롯의 계열만 추가한다
- `origin=USER` 인 TC는 건드리지 않는다
- 사용자가 수정한 TC도 건드리지 않는다

**수정 여부 판별.** `TestCase`에는 수정 표시 필드가 없다. 별도 필드를 추가하는 대신
`testcases` 테이블에 두 열을 둔다.

| 열 | 의미 |
|---|---|
| `generated_hash` | 생성 직후 TC 본문의 해시 |
| `slot_keys` | 이 TC를 만든 근거 슬롯 키 목록 |

재생성 시 현재 본문의 해시가 `generated_hash`와 다르면 사용자가 손댄 것으로 보고
보존한다. 해시가 같으면 근거 슬롯이 바뀐 경우에 한해 교체한다. 필드를 도메인 타입에
넣지 않는 이유는 `TestCase`가 xlsx 출력과 공유되는 순수 데이터 타입이고, 수정 추적은
저장소의 관심사이기 때문이다.

## 7. 에러 처리

인터뷰어가 Claude Code로 바뀌면서 LLM 호출 실패·재시도·예산 초과는 harness의 몫이
되었다. 남는 것은 CLI 자체의 실패다.

| 상황 | 처리 |
|---|---|
| 없는 슬롯 키로 `slot set` | **무시하지 않고** 사용 가능한 키 목록과 함께 오류. 조용히 성공하면 답변이 증발한 것처럼 보인다 |
| `slot init` 없이 `slot set` | 컨텐츠가 없다고 알리고 `slot init` 을 안내 |
| 같은 컨텐츠에 `slot init` 재실행 | 기존 슬롯 값을 보존하고 새 유형의 슬롯만 추가 |
| `tc add` 계열 위반 | 거부 + `tc plan` 안내 (§6) |
| `tc add` JSON 스키마 위반 | 어느 필드가 틀렸는지 짚어 거부 |
| DB 잠금 (동시 실행) | 재시도 후 실패 시 "다른 qatc 프로세스가 실행 중" |
| xlsx 제어문자 | `export/excel.py`에 sanitize 추가 |

**답변 유실은 구조적으로 방지된다.** `slot set` 이 실패해도 사용자 답변은 Claude Code
트랜스크립트에 남아 있어 재실행하면 된다. 원래 설계에서 "답변을 먼저 커밋한다"로
방어하던 문제가 harness 덕에 사라진다.

## 8. 테스트 전략

인터뷰 루프가 harness로 넘어갔으므로 `FakeLlmClient` 는 필요 없다. 테스트 대상은
**저장소와 게이트**로 좁혀지고, 그만큼 결정론적이 된다.

| 대상 | 방식 | 핵심 검증 |
|---|---|---|
| 슬롯 세트 조립 (`slots.py`) | 순수 함수 단위 | 유형 복수 적용 시 키 중복 병합(앞이 이김), 기본+유형 순서 |
| 슬롯 상태 전이 | 단위 | `empty→filled→na` 전이, `na`는 `slot status` 의 질문 대상에서 빠짐 |
| `slot set` 입력 검증 | CLI 단위 | 없는 키 · 빈 값 · 잘못된 status 를 오류로 반환 |
| `slot init` 재실행 | 임시 SQLite | 기존 값 보존, 새 유형 슬롯만 추가 |
| **`tc plan` 계열 계산** | 단위 | **빈/unknown/na 슬롯의 계열이 목록에서 빠진다** |
| **`tc add` 게이트** | CLI 단위 | **plan에 없는 계열을 거부한다** ← 가장 중요 |
| 재생성 병합 | 단위 | `generated_hash` 불일치 시 보존, `origin=USER` 불변 |
| `knowledge` 커버리지 출력 | 단위 | 분자·분모가 슬롯 상태와 일치 |
| xlsx 출력 | 실제 openpyxl | 제어문자 포함 문자열이 크래시 없이 나감 (회귀) |

굵게 표시한 두 항목이 이 설계의 불변식이다. 프롬프트로 부탁한 규칙이 아니라 코드가
강제하는 계약이고, 리팩터링 중에 깨지면 근거 없는 TC가 만들어지는데 아무도 눈치채지
못한다. 반드시 테스트로 못박는다.

반대로 "생성된 TC의 내용이 좋은가"와 "인터뷰가 좋은 질문을 했는가"는 테스트로 잡을 수
없다. 전자는 `origin` 구분과 `rationale` 추적성으로 **사람이 검토할 수 있게** 만드는
것으로, 후자는 `slot status` 커버리지 표시로 **빠진 것이 보이게** 하는 것으로 대응한다.
