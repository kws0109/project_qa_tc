# 게임 창 캡처 설계

**작성일:** 2026-08-15
**선행 설계:** [2026-08-14-qatc-app-design.md](2026-08-14-qatc-app-design.md)
**선행 구현:** [../plans/2026-08-15-app-usability.md](../plans/2026-08-15-app-usability.md) (스크린샷 첨부)

## 목표

채팅창의 버튼 하나로 **게임 창을 찍어 첨부한다.**

지금은 `Win+Shift+S` → 영역 드래그 → 채팅창에 `Ctrl+V` 다. 그것도 첨부 기능이
생긴 뒤의 이야기이고, 그 전에는 파일로 저장해 끌어다 놓아야 했다. 남은 문제는
**촬영 대상이 매번 같다는 것** — 인터뷰 한 번에 같은 게임 창을 여러 번 찍는데
매번 영역을 다시 그린다.

대상이 고정이면 고르게 할 이유가 없다. 게임 창을 프로파일에 못 박고, 버튼은
누르기만 한다.

## 왜 브라우저 화면 공유가 아닌가

`navigator.mediaDevices.getDisplayMedia()` 는 호출할 때마다 브라우저 선택창을
강제한다. 이것은 보안 게이트라 **페이지가 대상 창을 미리 지정할 수 없다** —
설정으로 우회할 방법이 없다. 즉 "창을 고정한다" 는 백엔드 캡처로만 성립한다.

스트림을 살려 두면 선택창을 첫 1회로 줄일 수 있다. 그러나 트랙이 살아 있는 동안
OS 캡처 파이프라인이 상주하고, 이 도구가 쓰이는 시점은 **게임이 GPU 를 쓰고 있는
때**다. 소유자가 그 상주 비용을 거부했고, 그 판단이 이 설계의 출발점이다.

## 제약

- Windows 전용. 사용자 1명(도구 소유자). 배포 계획 없음.
- **백엔드는 지식 DB 에 쓰지 않는다.** 캡처는 지식 루트를 전혀 건드리지 않는다
  (행동 스냅숏 가드가 파일과 폴더 mtime 으로 지킨다).
- `qatc/app/` 안의 어떤 파일도 지식 DB 쓰기 메서드 이름을 담지 않는다.
- 사용자에게 보이는 문자열은 한국어. 오류는 **다음 조치**를 함께 알린다.
- 캡처 결과는 **곧바로 전송되지 않는다.** 첨부 스트립에 들어가고 사용자가 보고
  뺄 수 있다 — 화면에 있는 것이 그대로 넘어가는 기능이므로 고를 기회가 반드시
  있어야 한다.
- 경로는 `pathlib.Path`. 콘솔 출력은 `qatc/console.py` 의 `_p()`.

## 1. 실측 — 이 설계의 전제

설계 전에 이 기계에서 직접 확인한 것이다. 안 되는 것을 전제로 쓴 설계는 계획
전체를 틀리게 만든다.

| 확인한 것 | 결과 |
|---|---|
| 창 열거 · 제목 · 사각형 조회 | 동작 (보이는 창 9개) |
| 프로세스 이름 조회 | 동작 |
| 창 사각형만 잘라 화면 스크랩 | 2574x1399, 고유색 5223 — 내용 정상 |
| `PrintWindow(PW_RENDERFULLCONTENT)` | 5개 중 4개 rc=1 · 내용 있음 |
| 같은 호출 | 1개 rc=0 · **고유색 1 (단색)** |
| 데스크톱 크기 | 5120x1440 |

**결론 세 가지.**

1. `PrintWindow` 는 대개 성공하지만 **실패가 이 기계에 실재한다.** 폴백은 이론상
   대비가 아니라 반드시 타는 경로다.
2. 실패는 `rc=0` 으로 드러났다 — 반환값을 1차 신호로 쓸 수 있다. 다만 rc=1 인데
   검은 화면이 나오는 사례(가속 렌더링 창)가 알려져 있으므로 단색 검사를 2차로
   둔다.
3. 성공 사례의 최소 고유색이 576, 실패 사례가 1이다. 그 사이는 넓으므로 단색
   판정 문턱을 보수적으로 잡아도 오판이 없다.

## 2. 경계와 컴포넌트

```
[촬영] 버튼 (app.js)
      │  POST /api/capture {game}
      ▼
qatc/app/server.py  ── 검증(Origin·JSON·game) · 오류를 한국어 HTTP 로 변환
      │
      ▼
qatc/capture.py     ── 창 선택(순수) + 찍기(OS 어댑터)
      │
      ▼
qatc/profiles.py    ── profiles/<게임>.yaml 의 window.process / window.title_regex
```

**`qatc/capture.py` 를 `qatc/app/` 아래에 두지 않는 이유.** 그 폴더는 무쓰기
가드가 **이름 대조로** 감시하는 영역이고, 캡처는 앱 전용이 아니라 게임 도메인
기능이다(뒤에 CLI 에서 쓰게 될 수도 있다). 그리고 Flask 없이 단위 테스트할 수
있어야 한다.

**`qatc/profiles.py` 는 죽은 값을 되살린다.** `profiles/*.yaml` 에는 이미
`window.process` 와 `window.title_regex` 가 네 게임 모두 실측값으로 들어 있는데,
녹화 파이프라인이 삭제되면서 `GameProfile` 이 `name` 만 읽게 됐다. 파일에 달린
"코드에서 읽지 않는다" 주석은 이 작업 뒤 거짓이 되므로 함께 고친다.

## 3. 창 선택 — 순수 함수

OS 를 만지는 부분과 **고르는 규칙**을 가른다. 규칙 쪽이 틀리기 쉬운 곳인데,
붙여 두면 실제 창 없이는 한 줄도 검사할 수 없다.

```python
@dataclass(frozen=True)
class WindowInfo:
    handle: int
    title: str
    process: str          # 예: "StarRail.exe" (소문자 비교)
    rect: tuple[int, int, int, int]   # left, top, right, bottom (물리 픽셀)
    minimized: bool

def select_window(candidates: Sequence[WindowInfo], profile: GameProfile) -> WindowInfo
```

**규칙.**

1. **최소화된 창은 먼저 뺀다.** 최소화된 창은 사각형이 화면 밖(음수 좌표)에
   있어 스크랩이 무의미하다. 그 다음 `profile.window_process` 가 있으면 프로세스
   이름으로 거른다 (대소문자 무시). 없으면 `profile.window_title_regex` 로 제목을
   거른다. 둘 다 없으면 설정 오류로 거절한다 — 아무거나 고르면 엉뚱한 창을 찍는다.
2. 프로세스로 걸렀는데 `title_regex` 도 있으면 **둘 다** 적용한다. 런처와 본
   게임이 같은 실행 파일인 경우가 있다.
3. 남은 것이 0개면, 최소화된 창까지 포함해 다시 본다. 거기서 찾으면 "최소화됨"
   이라는 **다른 오류**를 낸다 — "게임이 안 떠 있다" 와 다음 조치가 다르다.
4. 2개 이상이면 **면적이 가장 큰 창**을 고른다. 게임은 런처·오버레이 같은 작은
   보조 창을 함께 띄운다. 이것은 추측이 아니라 못 박은 규칙이고 테스트가 고정한다.
5. 면적이 같으면 목록 순서가 앞선 것. 결정적이어야 테스트가 성립한다.

**오류 종류.** 문구가 아니라 **코드**로 구분한다 — 소비자(라우트)가 렌더링된
한국어를 다시 뒤져 분기하면 문구를 고칠 때 조용히 깨진다. 이 프로젝트가
`unknown_session` 판정에서 이미 겪은 실패다.

| 종류 | 언제 |
|---|---|
| `no_window_config` | 프로파일에 `process` 도 `title_regex` 도 없다 |
| `not_running` | 최소화된 것까지 봐도 후보가 없다 |
| `minimized` | 최소화된 창에서만 찾았다 |

## 4. 캡처 — OS 어댑터

```python
def grab_window(info: WindowInfo) -> bytes     # PNG
```

1. `PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT)`.
   `rc == 1` 이고 단색이 아니면 성공. **가려져 있어도 찍힌다** — 이것이 이
   경로를 1순위로 두는 이유다.
2. 실패하면 **가려짐을 검사한다.** 창 사각형 안 9개 지점에서 `WindowFromPoint`
   의 루트 창이 대상인지 본다. 한 점만 보면 투명 영역·둥근 모서리에서 오판한다.
3. 안 가려져 있으면 화면 스크랩(`ImageGrab.grab(bbox, all_screens=True)`).
4. 가려져 있으면 **찍지 않고 거절한다.** 조용히 브라우저를 찍어 첨부하는 것이
   이 기능의 최악의 실패 모양이다 — 사용자는 게임을 보냈다고 믿는다.

**단색 판정.** 160x90 으로 줄인 뒤 고유색이 8 이하면 단색으로 본다. 실측에서
성공 사례의 최소가 576, 실패가 1이었다.

**DPI.** `SetProcessDPIAware()` 를 부르지 않으면 `GetWindowRect` 가 논리 픽셀을
돌려줘 스크랩 영역이 어긋난다(125% 배율에서 오른쪽·아래가 잘린다). 이 호출은
**프로세스 전역**이고 되돌릴 수 없으므로, import 시점이 아니라 **첫 캡처 때
한 번만** 부른다 — 캡처를 한 번도 안 쓰는 실행(테스트 스위트 전체가 그렇다)의
전역 상태를 바꾸지 않기 위해서다.

## 5. 크기

긴 변이 2560 을 넘으면 비율을 유지해 줄인다. 첨부 상한이 한 장 8MB 인데
5120x1440 이나 4K 창을 그대로 PNG 로 만들면 그 벽에 부딪히고, 사용자에게는
빨간 줄만 보인다. 2560 이면 UI 글자가 읽히면서 상한 안에 들어온다. PNG 를
유지한다 — JPEG 아티팩트가 글자에 끼면 QA 용도로 나쁘다.

## 6. HTTP API

### `POST /api/capture`

요청 `{"game": "starrail"}`.

**검증은 `/api/chat` 의 삼중 관문을 그대로 쓴다** — Origin(교차 출처 거절) ·
콘텐츠 타입 · 본문. 이 프로젝트가 결함을 낸 자리가 정확히 "검증 없는 새 POST"
였다. 이 엔드포인트는 돈이 들지는 않지만 **화면 내용을 돌려주므로** 교차 출처
차단이 오히려 더 중요하다. `game` 은 `resolve_db_path` 와 같은 방식으로 실재하는
목록과 대조한다.

성공 200:

```json
{"data": "<base64 PNG>", "media_type": "image/png"}
```

모양이 `POST /api/chat` 의 `images[]` 원소와 **같다** — 프런트가 캡처 결과를
붙여넣은 이미지와 구분 없이 다룰 수 있고, 백엔드의 `decode_shots` 검증(매직
바이트·크기)도 그대로 한 번 더 지난다. 폭·높이는 싣지 않는다: 화면에 이미
썸네일이 보이고, 아무도 안 쓰는 필드는 다음 사람에게 "이걸 봐야 하나" 라는
질문만 남긴다.

실패는 전부 `{"error": "<한국어 한 문장>"}` 와 상태 코드. 프런트는 그 문장을
그대로 보여준다. 캡처 쪽 오류 종류(위 표 + `occluded` · `blank`)를 라우트가
상태 코드로 옮긴다.

## 7. 프런트

`[촬영]` 버튼 하나. 누르면 `/api/capture` → 받은 base64 를 `File` 로 만들어
**기존 `addImageFiles()` 에 투입한다.** 4장/8MB 검증·썸네일·`x` 제거·전송이
전부 재사용되고, 캡처 전용 업로드 경로는 만들지 않는다.

촬영 중에는 버튼을 비활성화한다(연타로 4장이 순식간에 차는 것을 막는다).
실패하면 기존 오류 줄로 한국어 한 문장.

## 8. 실패 처리

| 상황 | 상태 | 문구가 담아야 할 다음 조치 |
|---|---|---|
| 프로파일에 `window` 없음 | 400 | `profiles/<게임>.yaml` 에 `window.process` 를 넣으라고 |
| 창을 못 찾음 | 404 | 게임이 실행 중인지 확인하라고 |
| 창이 최소화됨 | 409 | 창을 복원한 뒤 다시 누르라고 |
| `PrintWindow` 실패 + 가려짐 | 409 | 게임 창을 가리지 말라고 (나란히 두라고) |
| `PrintWindow` 실패 + 안 가려짐인데도 단색 | 409 | 전체화면 배타 모드는 못 찍는다고, 테두리 없는 창 모드나 `Win+Shift+S` 붙여넣기를 권함 |
| 게임 이름이 목록에 없음 | 404 | 트리에서 고르라고 |

## 9. 테스트 전략

**순수 규칙은 전부 단위 테스트한다.** `select_window` 에 만든 `WindowInfo`
목록을 넣어 검사한다 — 프로세스 일치, 제목 정규식 일치, 둘 다 적용, 없음,
최소화만 있음, 복수 일치에서 큰 창, 면적 동률.

**OS 어댑터는 얇게 두고 라우트 테스트에서 스텁한다.** 실제 Win32 경로는 테스트
스위트가 아니라 **라이브 확인**으로 본다. 직전 작업에서 555건이 전부 초록인 채
기능이 죽어 있었고 그것을 잡은 것이 라이브 확인이었다 — 같은 함정이 여기서 더
크다(창 상태는 CI 로 재현할 수 없다).

**무쓰기 가드에 `/api/capture` 를 추가한다.** 새 엔드포인트가 지식 루트를
건드리지 않는지 파일과 폴더 mtime 으로 확인한다.

**새 테스트는 전부 뮤테이션으로 검증한다.** 구현을 깨뜨려 그 테스트가 실패하는지
보고 에디터로 복원한다.

## 10. 만들지 않는 것

- **영역 선택(크롭) UI.** 창 전체를 찍는다. 크롭이 필요하면 `Win+Shift+S` 가
  이미 있고 붙여넣기로 들어온다.
- **여러 창 동시 캡처 · 전체 데스크톱 캡처.** 후자는 소유자가 개인정보를 이유로
  거부한 안이다.
- **캡처 이력·저장.** 첨부는 턴이 끝나면 지워진다. 그대로 둔다.
- **배타 전체화면 우회(DXGI Desktop Duplication).** 안내로 처리한다. 창 모드
  전환이 훨씬 싸다.
- **캡처 단축키.** 버튼 하나로 충분한지 먼저 쓰고 판단한다.

## 11. 열려 있는 항목

- `profiles/bluearchive.yaml` 은 `process` 가 빈 문자열이고 `title_regex` 가
  넓다(에뮬레이터 여러 종). 오탐 가능성이 있으나, 실제로 그 게임으로 인터뷰할
  때 확인하면 된다 — 지금 추측으로 좁히지 않는다.
- 게임 창이 두 모니터에 걸쳐 있을 때. `all_screens=True` 로 뜨는지 라이브에서
  확인한다.
