# TC 테이블 재설계 — 계층 · 범위 · ID

**작성일:** 2026-08-16
**선행 설계:** [2026-08-14-interview-driven-tc-design.md](2026-08-14-interview-driven-tc-design.md)
**참고 자료:** 테스트케이스 Depth 작성법(august-jhy.tistory.com/135) · 테스트 케이스 작성 방법(brunch.co.kr/@sj-jo/13)

## 목표

첫 실사용의 산출물(`로그인` TC 23건)을 사람이 읽을 수 있는 표로 만든다.

지금 표는 이렇게 읽힌다:

| 대분류 | 중분류 | 제목 |
|---|---|---|
| 로그인 | 경계값 | 비밀번호 두 필드가 불일치하면 연동하기 버튼 비활성 유지 |

세 가지가 잘못돼 있다.

1. **중분류가 계층이 아니라 방법론이다.** `경계값`·`실패 경로` 는 QA 가 아는 것이지 표가 말할 것이 아니다. 소유자의 말: *"테스트 케이스에 어떤 방법론인지 적은건 본적이 없음"*.
2. **구체성이 전부 제목 한 문장에 몰려 있다.** 계층은 아무것도 좁히지 못하고, 자매 케이스(비밀번호 일치/불일치/한쪽만)가 표에서 나란히 보이지 않는다.
3. **TC ID 가 `tc_023a0e9dc6`** — 무작위 uuid 라 정보가 0이고, 재생성할 때마다 바뀐다.

목표는 **대분류 + 중분류 + 소분류만 읽어도 어떤 테스트인지 알 수 있는 표**다. 제목 칸은 없앤다.

## 제약

- Windows 전용. 사용자 1명(도구 소유자).
- 사용자에게 보이는 문자열은 한국어. 오류는 다음 조치를 함께 알린다.
- **계열(family)은 사라지지 않는다.** 게이트(`plan_families`)가 "근거 없는 TC 는 만들지 않는다" 를 강제하는 단위이고, 근거 철회 판정도 계열 단위다. **시트에서만 뺀다.**
- 기존 `로그인` 23건은 첫 실사용의 결과물이다. 손실 없이 옮긴다.
- 경로는 `pathlib.Path`. 콘솔 출력은 `qatc/console.py` 의 `_p()`.

## 1. 계층의 의미

| | 담는 것 | 예 |
|---|---|---|
| 대분류 | 화면·기능 영역 (= 컨텐츠 이름) | `로그인` |
| 중분류 | 그 안의 메뉴·화면·기능 단위 | `신규 계정 연동` |
| 소분류 | 거기서 확인하는 **케이스 이름** | `비밀번호 불일치` |

**소분류에 결과를 적지 않는다.** 결과는 `기대결과` 컬럼이 이미 갖고 있다. 이 규칙이 소분류를 짧게 만들고, 자매 케이스를 나란히 세운다:

| 대 | 중 | 소 | 기대결과 |
|---|---|---|---|
| 로그인 | 신규 계정 연동 | 비밀번호 일치 | 연동하기 버튼 활성화 |
| 로그인 | 신규 계정 연동 | 비밀번호 불일치 | 연동하기 버튼 비활성 유지 |
| 로그인 | 신규 계정 연동 | 비밀번호 한쪽만 입력 | 연동하기 버튼 비활성 유지 |

판정 규칙: **소분류만 떼어 읽었을 때 모호하면 중분류가 잘못 잡힌 것이다.**

## 2. 하나의 TC 가 담는 범위

기대결과가 여럿일 때 나눌지 합칠지는 **판단**이다. 세면 되는 값이 아니다.

### 규칙

1. **독립된 결과면 나눈다.** 하나의 입력에 서로 다른 영역·비즈니스 로직이 작동해 여러 결과가 나오는 경우다. 확인 수단이나 시점이 갈리는 것이 신호다.
   - 예: 회원가입 버튼 클릭 -> `DB 에 사용자 정보가 저장된다` / `가입 완료 환영 이메일이 발송된다`
   - DB 조회와 메일함 확인은 다른 수단이고, 한쪽이 실패해도 다른 쪽은 독립적으로 검증돼야 한다. **2건으로 나눈다.**
2. **연속·종속이거나 한 화면의 한 세트면 합친다.** 하나의 흐름으로 이어져 있거나 UI 상태 변화를 동시에 확인하는 경우다.
   - 예: 로그인 성공 -> `메인 페이지로 이동하고 상단에 '홍길동님 환영합니다' 가 노출된다`
   - 화면 전환과 문구 노출이 한 세트다. **1건으로 유지한다.**
3. **세트여도 확인이 6개를 넘으면 영역별로 나눈다.** 규칙 2를 그대로 두면 기대결과 11개짜리가 살아남는데, 11개 중 7번째만 없어도 표에는 `FAIL` 만 남고 **어디가 문제인지 사라진다.** 개당 3~4개가 되게 영역으로 묶는다(상단 영역 / 입력 영역 / 약관·버튼 영역).

규칙 1·2 는 판단이고 규칙 3만 기계적이다. 그래서 **강제는 규칙 3 에만 걸고(경고), 1·2 는 `SKILL.md` 가 위 두 예시로 가르친다.**

### 왜 하드 거부가 아닌가

한때 "`expected` 는 정확히 1개" 로 강제하려 했다. 근거는 "두 사실이 정말 하나의 확인이면 한 문장으로 쓰면 되므로 막히는 정당한 경우가 없다" 였는데, **그 근거가 거짓이다.** 회원가입의 DB 저장과 이메일 발송은 한 문장으로 이어 쓰면 안 되는 서로 다른 검증이다. 판단이 필요한 기준을 코드가 셀 수는 없다.

### 실측 (23건)

기준을 기대결과가 2개 이상인 17건 전부에 적용한 결과다.

| 판정 | 건수 | 대표 예 |
|---|---|---|
| 합침 | 10 | `오류창이 표시된다` + `닫으면 초기 화면으로 돌아간다` (종속) · `로그인 완료` + `게임시작 버튼` + `서버 상태` (한 화면 세트) |
| 분리 | 7 | `연동하기 버튼 활성`(UI) vs `계정 생성`(백엔드) · `모달 요소 표시` vs `가입이 진행되지 않는다`(차단 로직) |

**23건 -> 약 32건.**

기준을 세우기 전 한때 `기대결과 1개 = TC 1개` 로 잡았을 때는 73건(3.2배)이었다. 그 규칙은 종속된 흐름까지 쪼개 절차를 불필요하게 반복시켰다.

**절차 중복 자체는 비용이 아니라 요구사항이다.** 규칙 1로 나뉜 두 TC 가 같은 앞 절차를 반복하는 것은 옳다 — 독립성은 각 케이스가 혼자 실행 가능해야 성립한다. 표에 같은 절차가 여러 번 보이는 것을 결함으로 오해하지 말 것.

## 3. TC ID

```
TC_LOGIN_001
|  |     +-- 컨텐츠 안의 일련번호, 001부터, 3자리 (999 초과 시 자릿수 확장)
|  +-- 대분류(컨텐츠)의 라틴 약어
+-- 고정 접두사
```

**중분류를 넣지 않는다.** 넣으면 재분류할 때마다 ID 가 바뀌고, 이미 버그 리포트에 인용된 ID 가 죽는다 — 추적성이라는 ID 의 존재 이유와 정면으로 충돌한다. 대분류만 쓰면 그 문제가 아예 없다.

**라틴 약어는 인터뷰를 진행하는 모델이 정한다.** 로마자 표기로는 안 된다 — `로그인` 의 로마자는 `logeuin` 이라 `LOGIN` 이 안 나온다(영어 login 을 한글로 적은 말이라 되돌리면 깨진다). 모델은 `로그인 -> LOGIN`, `파티편성 -> PARTY` 를 정확히 아는 반면 사용자는 아무것도 입력하지 않으므로, 사용자 자리에서 보면 자동이다.

- `qatc slot init <컨텐츠> --code LOGIN` — `SKILL.md` 가 항상 붙이도록 지시한다
- 코드는 `contents.code` 에 저장하고 **한 번 정해지면 고정**한다
- `A-Z0-9` 2~12자만 허용. 같은 DB(=같은 게임) 안에서 중복이면 거부하고 다른 코드를 쓰라고 알린다
- **코드가 없으면 지어내지 않고 거부한다.** 기계가 만든 `TC_C01_001` 보다 "무엇을 하라"까지 적힌 한국어 오류가 낫다

### 번호의 안정성

지금 `replace_generated` 는 한 계열을 재생성할 때 생성분을 지우고 새로 넣는다 — 무작위 uuid 라 티가 안 났을 뿐, **매번 ID 가 갈린다.** 두 가지로 고친다.

1. **같은 `(중분류, 소분류)` 면 같은 TC 로 보고 번호를 물려준다.** 소분류가 케이스 이름이 되면서 이 대조가 가능해졌다.
2. **번호는 컨텐츠 안에서 단조 증가하고 재사용하지 않는다.** 지워진 번호는 비워 둔다.

둘은 모순이 아니다 — 물려받기는 **같은 케이스**가 자기 번호를 유지하는 것이고, 재사용 금지는 **다른 케이스**가 남의 번호를 물려받지 않는다는 것이다.

보장하는 것과 하지 않는 것을 분명히 한다 — 내용이 바뀐 TC 가 같은 번호를 유지한다고는 보장하지 않는다. 보장하는 것은 **한 번 발급된 번호가 다른 TC 에게 재사용되지 않는다**는 것이다. 버그 리포트가 가리키던 번호가 엉뚱한 TC 를 가리키는 최악을 막는 것이 목적이다.

## 4. 데이터 모델

`TestCase` 에 두 필드를 더한다.

```python
category_sub: str = ""     # 소분류 (케이스 이름)
family: str = ""           # 계열 - 지금까지 category_minor 가 대신하던 값
```

**`family` 를 필드로 올리는 이유가 이 변경의 핵심 위험이다.** 지금 여덟 자리가 `tc.category_minor` 를 계열의 **대용품**으로 읽는다 (앱 트리 그룹, 근거 철회 판정 3곳, `tc list` 출력, xlsx 통계). `category_minor` 에 다른 값이 들어가는 순간 그 여덟 자리가 **조용히** 틀린다 — 예외도, 빈 결과도 아니고 그냥 잘못된 분류가 나온다. 필드를 만들어 소비자를 옮기면 그 이동을 테스트가 강제할 수 있다. DB 에는 이미 `testcases.family` 컬럼이 있으므로 값의 출처도 새로 만들 것이 없다.

**`title` 필드는 지우지 않는다.** 지우면 기존 23건의 정보가 증발한다. 새 TC 는 쓰지 않고, 시트에서 빠지고, 화면은 소분류로 라벨링하되 비어 있으면 제목으로 폴백한다.

`contents` 테이블에 `code TEXT NOT NULL DEFAULT ''` 를 더한다.

**기존 행과의 호환.** `TestCase.from_row` 는 `cls(**row)` 이므로, 기본값 있는 필드를 더하면 그 키가 없는 옛 행도 그대로 읽힌다. 마이그레이션은 이 발판 위에서 값을 채운다.

## 5. 엑셀 시트

`테스트케이스` 시트:

```
TC ID · 대분류 · 중분류 · 소분류 · 사전조건 · 절차 · 기대결과 · 우선순위 · 출처 · 근거 · 근거 상태
```

- `제목` 제거 — 대/중/소가 그 일을 한다
- `유형` 제거 — `정상 경로`·`경계값` 이 들어가던 칸이고, 방법론을 개별 TC 에 적지 않는다는 결정이 여기에도 적용된다
- `소분류` 추가

`기대결과` 는 여러 줄일 수 있다(2절의 규칙 2). 지금처럼 `- ` 글머리로 이어 붙인다.

**남기는 것과 그 이유.** `출처`(인터뷰/추론됨)는 방법론이 아니라 **출처**다 — "담당자가 말한 것" 과 "우리가 도출한, 미검증인 것" 의 구분이라 표에 값이 있다. `근거`(어느 슬롯의 어떤 진술에서 나왔는지)와 `근거 상태`는 참고 자료가 말하는 **추적성**을 일반적인 TC 시트보다 강하게 만족시키는 부분이라 그대로 둔다.

`미확인 항목` 시트는 바꾸지 않는다 — 거긴 커버리지 이야기라 계열이 맞는 자리다. `요약` 의 "유형별" 집계도 유지한다(개별 TC 에 방법론을 적는 것과 다른 일이다).

## 6. 입력 계약

### `qatc slot init`

`--code <라틴약어>` 를 받는다. **새 컨텐츠에는 필수**다.

이미 있는 컨텐츠에 재실행할 때는 세 갈래다. `--code` 를 생략하면 기존 코드를 그대로 둔다(유형만 덧붙이는 기존 용법이 그대로 동작해야 한다). 같은 코드를 주면 아무 일도 없다. **다른 코드를 주면 거부한다** — 그 코드로 ID 가 이미 발급됐고, 바꾸면 발급된 ID 와 어긋난다.

### `qatc tc add --json`

각 항목이 `middle`(중분류)·`sub`(소분류)를 **필수로** 받는다. `title` 은 더 이상 읽지 않는다.

```json
{"testcases": [
  {"middle": "신규 계정 연동", "sub": "비밀번호 불일치",
   "precondition": "...", "steps": ["..."], "expected": ["..."],
   "rationale": "..."}
]}
```

검증:

키 이름이 필드 이름과 다르다: `middle` -> `category_minor`, `sub` -> `category_sub`. 짧은 키를 쓰는 이유는 이 JSON 을 모델이 손으로 쓰기 때문이다(`category_minor` 는 지금 계열을 담고 있어 이름 자체가 오해를 부른다).

- `middle`·`sub` 가 비었으면 거부한다. 판정은 `qatc/knowledge/models.py` 의 `is_blank` 를 쓴다 — `strip()` 은 제로폭 공백·한글 필러를 하나도 지우지 않는다(이 저장소가 이미 겪은 결함).
- **`expected` 가 비었으면 거부한다.** 확인할 것이 없는 TC 는 TC 가 아니다.
- **`expected` 가 6개를 넘으면 경고한다. 막지는 않는다.** 2절의 규칙 3을 코드가 거드는 자리다 — 세면 되는 값이라 오탐이 없다. 규칙 1·2 는 판단이라 코드가 셀 수 없으므로 강제하지 않는다.
- **소분류가 25자를 넘으면 경고한다. 막지는 않는다.** 길다는 것은 결과를 밀어 넣었거나 두 케이스가 붙었다는 신호이지 그 자체가 오류는 아니다 — `저장 및 종료` 같은 버튼 이름이 정당하게 들어갈 수 있다. 여기는 정당한 예외가 실재하므로 막으면 그 예외를 표현할 방법이 없어진다.

## 7. 스킬 규칙

`SKILL.md` 의 3단계에 넣는다. 나쁜 예는 지어내지 않고 **지금 산출물에서 가져온다.**

- 중분류에 방법론을 적지 않는다. 나쁜 예: `경계값`. 좋은 예: `신규 계정 연동`
- 소분류에 결과를 적지 않는다. 나쁜 예: `비밀번호 불일치 시 연동하기 버튼 비활성 유지`. 좋은 예: `비밀번호 불일치`
- **독립된 결과는 나누고, 연속·종속된 결과는 합친다** (2절). 나누는 예: `연동하기 버튼이 활성된다`(UI) 와 `신규 계정이 생성된다`(백엔드) — 확인 수단이 다르다. 합치는 예: `오류창이 표시된다` 와 `닫으면 초기 화면으로 돌아간다` — 하나의 종속된 흐름이다
- **세트여도 확인이 6개를 넘으면 영역별로 나눈다.** 11개를 한 줄에 묶으면 7번째만 틀려도 어디가 문제인지 표에서 사라진다
- 기대결과를 모호하게 적지 않는다. 나쁜 예: `버튼이 노출된다`. 좋은 예: `연동하기 버튼이 회색 비활성 상태로 표시된다`
- 조작 대상을 특정한다. 나쁜 예: `버튼을 클릭한다`
- 사전조건에 주체를 적는다 — 초기화가 수동인지 자동인지
- 기획 변경에 견디게 쓴다. 화면의 우연한 세부에 지나치게 붙은 케이스는 회귀 때 대량 수정을 부른다

## 8. 앱 화면

- 왼쪽 트리의 **계열 묶음은 유지한다** — 거기는 게이트 커버리지를 보는 자리라 계열이 맞다. TC 라벨만 소분류로 바뀐다(비면 제목으로 폴백).
- 오른쪽 검토 패널의 제목 자리에 `중분류 > 소분류` 를 보여준다.
- 트리·검토 패널이 계열을 읽던 자리는 `tc.family` 로 옮긴다.

## 9. 기존 23건 마이그레이션 (23 -> 29)

기계적으로 못 한다 — 제목·절차·근거를 읽고 판단해야 한다. 그래서 **판단을 먼저 끝내 데이터로 만들어 두고**, 구현은 그것을 적용하기만 한다.

승인된 분류의 성질(구현이 검산할 값):

| | 값 |
|---|---|
| 행 | 29 (기존 23 + 분리로 6) |
| 중분류 | 7 — 클라이언트 실행 2 · 로그인 창 2 · 소셜 연동 6 · 신규 계정 연동 11 · 약관 동의 5 · 재로그인 2 · 로그인 완료 1 |
| 기대결과 총합 | 70 (원본 73 — 아래 메모 참고) |
| 기대결과 최대 | 6 (2절 규칙 3의 상한과 같다) |
| ID | `TC_LOGIN_001` ~ `TC_LOGIN_029` |

**원본에서 줄어든 유일한 자리.** 기존 15번이 갖고 있던 약관 모달의 제목·본문·버튼 3줄은 `TC_LOGIN_022` 와 글자까지 같아 그쪽에만 남겼다. 73 -> 70 의 차이가 이것뿐이며, 다른 기대결과는 한 줄도 사라지지 않는다.

1. `로그인` 에 `code = LOGIN` 을 부여한다.
2. **이 단계는 이미 끝났다.** 23건에 2절의 세 규칙을 적용한 분류표를 만들어 소유자의 승인을 받았고, 결과는 **29건**이다. 그 판단은 기계가 읽을 수 있는 형태로 저장소에 있다:
   [`docs/superpowers/2026-08-16-login-reclassify.json`](../2026-08-16-login-reclassify.json).
   구현은 판단을 다시 하지 않고 **그 파일을 적용만 한다.**
3. 승인 뒤 적용한다. **적용 전에 DB 파일을 복사해 백업한다** — 되돌릴 수 있어야 한다.
4. ID 를 `TC_LOGIN_001` 부터 다시 매긴다. 순서는 **중분류 묶음 순, 그 안에서는 소분류 순**이다 — 표를 위에서 아래로 읽을 때 번호가 증가해야 사람이 찾을 수 있다. 아직 어디에도 인용된 적 없는 uuid 라 지금이 바꿀 수 있는 마지막 시점이다.

`family` 필드는 DB 의 `testcases.family` 컬럼에서 채운다(값이 이미 있다).

## 10. 테스트 전략

- **계열 대용 사용의 제거를 테스트가 강제한다.** `category_minor` 에 계열이 아닌 값을 넣은 TC 로 트리·철회 판정·`tc list`·xlsx 를 태워, 계열로 착각하면 실패하게 한다. 이것이 이 변경의 유일한 조용한 실패 경로다.
- 엑셀 헤더와 행의 값을 컬럼 단위로 고정한다(`제목`·`유형` 이 없다는 것까지).
- ID 규칙: 형식, 컨텐츠 안 증가, `(중분류, 소분류)` 가 같으면 번호 물려받기, 번호 재사용 안 함, 코드 없으면 거부, 코드 중복 거부.
- `expected` 가 비면 **거부**되는지(rc=1, 저장 안 됨).
- 경고 2종(`expected` 6개 초과 · 소분류 25자 초과)이 실제로 뜨는지, 그리고 **막지는 않는지**(rc=0, 저장됨). 판단 규칙을 코드가 강제하지 않는다는 것 자체를 고정한다.
- 마이그레이션 후 모든 TC 가 중/소분류와 새 ID 를 갖고, 기대결과가 6개를 넘는 것이 없는지.
- 새 테스트는 전부 뮤테이션으로 검증한다.

## 11. 만들지 않는 것

- **`자기세정` 컬럼.** 참고 자료의 6가지 기준 중 하나지만, 1인용 게임 QA 도구에서 대부분의 케이스에 해당이 없다. 필요하면 사전조건에 적는다.
- **중분류 자동 추론.** 화면 인벤토리에서 메뉴 구조를 기계가 뽑는 것은 이 변경의 범위가 아니다. 모델이 인터뷰에서 정한다.
- **라틴 약어 자동 생성(로마자/사전).** 로마자는 틀린 답을 내고, 사전은 유지 대상이 된다. 모델이 정하고 CLI 가 검증한다.
- **기대결과별 결과(PASS/FAIL) 칸.** 규칙 1로 독립된 결과가 이미 별도 행이 되므로, 한 행에 남은 기대결과들은 함께 판정하는 한 세트다.
- **옛 ID 와 새 ID 의 매핑표.** uuid 는 아직 어디에도 인용된 적이 없다.

## 12. 열려 있는 항목

- 999건을 넘는 컨텐츠가 나오면 자릿수를 늘려야 한다. 지금은 23건이라 실제 문제가 아니고, 늘릴 때 옛 번호를 다시 매기지 않는다(`TC_LOGIN_0001` 과 `TC_LOGIN_001` 이 섞인다).
- 컨텐츠 이름을 바꾸면 코드는 그대로 둘지. 지금은 이름 변경 기능 자체가 없다.
